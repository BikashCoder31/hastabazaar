## Existing-account transition

The migration does not reset users, sessions, credentials, roles or existing business links. A customer or seller can continue existing password sign-in. On that account's **first successful email/Google verification**, old sessions are revoked and an unverified non-staff password is removed to prevent a password established before mailbox ownership from retaining access. The person can keep using email/Google sign-in and use **Forgot password** to establish a verified password. Login copy explains this. Password reset itself records mailbox proof and revokes earlier sessions.

Existing Admin/Super Admin passwords are deliberately retained for access continuity; first mailbox verification still revokes old sessions. Existing identity-bound staff roles are not re-approved or silently moved between users. New invitations require mailbox proof. This compatibility exception is not a retrospective guarantee that every historical privileged credential was originally mailbox-verified. The historical seller-access complaint remains unresolved without its own account/application evidence.

## Remaining limits and external acceptance

- No authenticated or anonymous production checks were performed during this implementation. Earlier audit live evidence remains historical.
- Google state/nonce/PKCE configuration tests and the verified-provider callback code were checked locally; real Google OAuth, inbox delivery and real-device GPS were not exercised. A later approved production verification should use designated test identities, including existing privileged access, without modifying unrelated users.
- The upload reader caps retained chunks before parsing; parsing/decoding adds bounded copies and native memory. No RSS load test or reverse-proxy upload-limit claim is made. Concurrent upload admission/CPU budgets remain future operational work.
- CSP retains `unsafe-inline` for framework scripts/styles. It provides useful restrictions but is not a nonce-based XSS solution. Local header/maps/media compatibility passed; external Google redirects need the later designated-account check.
- `TRUSTED_CLIENT_IP_HEADER` must remain unset until Babal confirms that the chosen proxy **overwrites** `x-real-ip` or `cf-connecting-ip` on every request. Never trust an arbitrary client-supplied value or merely assume a proxy is present. Account limits remain independent of IP. Unset configuration uses a shared authentication budget of 300 calls per 15 minutes and at least 300 for unscoped public budgets; each wrapper invocation counts, so some flows consume more than one call. Heavy shared traffic or abuse can still temporarily exhaust the shared fallback. Verified proxy behavior is needed for fair per-client isolation.
- Sharp is pinned to 0.35.2; Linux x64 Sharp and libvips archives are checked against package-lock SHA-512 before inclusion. Actual Babal Linux native execution is pending. The official [Sharp installation requirements](https://sharp.pixelplumbing.com/install/) list Linux x64 glibc >=2.28 and SSE4.2; optional platform dependencies must be retained. [Sharp output documentation](https://sharp.pixelplumbing.com/api-output/) describes default metadata removal, additionally verified with an EXIF-bearing local test image.
- No deposits/withdrawals were enabled. Existing referral rewards/discounts, order/return-policy snapshots, aftercare, manual courier references and rider-sharing limitations are preserved. Automatic couriers, email retry cron, parcel/COD reconciliation and release-specific readiness (audit F04) remain section 2 work.
