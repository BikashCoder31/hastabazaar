## Processing behavior

- deliverBusinessEmails accepts the existing EMAIL transport shape and a strict HTTPS application origin. Reject credentials, query/fragment, non-root origin paths, unsafe recipients/header newlines and unmapped links. An invalid global origin fails before claiming or consuming attempts.
- Atomic conditional claim with unique token and 15-minute lease; only the claimant finishes its row. Concurrent workers do not send the same live claim twice. Failed sends retain only delivery_failed and become eligible after five minutes, up to five attempts. Exhausted records need staff review; there is no automatic reset.
- Before every send, recheck active recipient, current effective staff permission, ownership, current exception assignment/open state, and pending reviewer/permission/payout action where relevant. Cancel revoked or obsolete recipients safely.
- SMTP acceptance cannot share a database transaction. A crash or connection ambiguity after SMTP acceptance may produce a duplicate on retry; no exactly-once/inbox/read-receipt promise is made. Sent means mail-server accepted.
- /admin/business-emails and its API are Super Admin-only (admin.invite reserved authority). Manual processing describes actual contact effect and attempts at most six eligible records. Existing authenticated actor audit records the processing result. Body capped at 1 KiB; staff permission change API capped at 16 KiB. No route was invoked against a real transport during this work.
