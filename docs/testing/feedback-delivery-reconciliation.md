# Feedback delivery reconciliation (support runbook)

The restricted `/admin/feedback` view shows all saved feedback jobs: pending, leased, retryable failed, exhausted failed/expired lease, uncertain sending, and confirmed sent. Each row shows its request ID, source/form ID, originating page path, and creation time in UTC alongside the message. Access requires an active staff account and a current `support.manage` grant. The request ID is an internal reference, not evidence of email delivery. Status is a snapshot and may change while another request runs.

1. Find the customer's request ID in the support view. Confirm the form/source, originating page, UTC creation time, address, topic, and message before discussing it with the customer. Do not copy custom answers into email or public tickets.
2. **Pending or leased:** the answer and job were saved, but a delivery attempt may be queued or in progress. A leased job can advance to `sending` or be retried after its lease expires; refresh the view before relying on its status. Do not infer that the mail was delivered or definitely unsent from a stale page.
3. **Delivery uncertain:** the job entered `sending` before the external transport call, or a request failed before acquiring the lease while another exact request could have progressed. The message may have been accepted even when the page says uncertain. Check the support mailbox and available transport records for a matching message and time. A missing message is not proof that no mail was sent. Do not automatically retry, manually edit the job to `sent`, or claim a verified delivery without independent evidence.
4. **Retryable failed:** a definite pre-send transport failure was durably recorded, and the same request ID remains below the five-attempt cap. An exact same-body retry can resume; changed content conflicts. **Attempts exhausted:** five definitely pre-send failures, or a final pre-send lease expired without entering `sending`, prevent another same-key attempt. Refresh before acting on a leased row and explain the current status to the customer.
5. If the status cannot be resolved, tell the customer that a new submission could create a duplicate. The customer may use **Start a new message after contacting support** in the same browser tab. The confirmation clears only the opaque session request ID; it does not alter the saved job or answer. A new submission uses a new ID and remains subject to ordinary rate limits.

This is a read-only reconciliation workflow. There is no support-side state mutation or replay of uncertain jobs, and no claim of exactly-once SMTP delivery. Escalate provider-log disputes through the normal support/operations process; do not run production SQL or migrations as part of this procedure.
