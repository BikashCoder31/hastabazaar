# Native MariaDB recovery

The Babal runtime uses MariaDB and filesystem media. Its Backup & Transfer page intentionally disables browser data exports and SQL restores. Super Admin can still download the separately encrypted security key recovery bundle after recent password and MFA verification. Local SQLite exports are a different format and cannot restore this host.

The native procedure preserves a **verified Linux release artifact**, a native database dump, every public/private media file and its metadata sidecar, and a separate encrypted key recovery bundle. Packaging does not establish that restoration succeeded. A hosting switch remains a separately reviewed operation.

## Prepare an operator snapshot

1. Identify the exact source database, media root, immutable release archive, and new private snapshot/output directories. Record their resolved paths and the source cutoff. Never use the active local `.staging` data, a recovery ZIP, or an existing destination as an implicit target.
2. Pause application writes, workers, mail/payment dispatch and scheduled database events at the host. Keep them paused through the database and media capture. A flag in a JSON file is an operator attestation, not a mechanism for stopping writes.
3. Use the host's `mariadb-dump` for the approved database with `--single-transaction --hex-blob --order-by-primary --skip-comments --skip-dump-date --routines --triggers`. Keep credentials in an operator-only defaults file, never command arguments, logs or the snapshot. Save stdout to `database.sql`. A native dump includes generated definitions/constraints and places table triggers after its records, avoiding replay of financial insert triggers during a new restore.
4. Copy all media under `media/public/` and `media/private/`, including each original `.metadata.json` sidecar. Symlinks, unknown paths, missing pairs and oversized packages stop packaging. Do not rewrite metadata or regenerate evidence files. Include the exact CI-verified archive as `release/artifact.tar.gz`.
5. Record the release ID, exact commit, archive SHA-256, native schema fingerprint, MariaDB version and key IDs. The existing CI inventory supplies release/commit/archive identity; `captureNativeInventory` in `scripts/recovery/native-inventory.mjs` supplies an exact schema/table/trigger inventory using bounded server-side binary encodings. No JavaScript numeric conversion is used for record hashes. Compare native inventories before and after capture. Unknown tables, routines/events or unsupported engines block the supported procedure.
6. From the matching reviewed source checkout with its locked dependencies installed, save a reviewed plan with `snapshot` and `output` absolute paths, a non-secret `writePauseEvidence` description, and `provenance` containing `release`, `artifactKind: "linux-release"`, `sourceSha256: null`, `commit`, `artifactSha256`, `schemaSha256`, `keyIds`, `engine`, `writeMode: "paused"`, and `dispatchPaused: true`. Run `node --import tsx scripts/recovery/package-native-backup.mjs --plan <reviewed-plan.json>`. Supply only a JSON object with a `passphrase` through private standard input; do not put it in arguments, shell history or the plan. The passphrase must have at least sixteen characters. These operator scripts run from source; the standalone application is not an operator shell.
7. Keep the resulting encrypted `.hzn` archive and its verification receipt outside the hosting account. Keep the separately encrypted `.hzk` key recovery bundle and its different passphrase separately. Protect or dispose of plaintext operator snapshot files under the organization's reviewed retention procedure. The tool never deletes those source files automatically.

The current bundle limit is 32 GiB of plaintext and 100,000 files; each encrypted chunk is bounded and this combination remains within the authenticated format's frame limit. Native inventory rejects any row above 512,000 bytes before transferring its contents through the database driver. Larger installations or rows require a separately tested backup method. Successful packaging records `restoreVerified: false` and `activationAllowed: false`.

## Rehearse before restoration

`scripts/verify-staging-native.mjs` owns a fresh loopback MariaDB container with no bind mounts. It imports only trusted repository schema, runs required accounting, financial, billing and MFA journeys without skips, and then invokes `scripts/recovery/rehearse-native.mjs`. The rehearsal:

- Validates the container identity and permits only its own new `native_<run>_recovery` target; occupied targets, arbitrary hosts and production/local databases are rejected.
- Recovers the exact CI release archive, synthetic native dump and public/private media through authenticated encrypted files, using the approved archive digest. A wrong key passphrase or altered archive fails closed.
- Restores native SQL only inside that owned container, using `mariadb --comments` to preserve trigger body comments and the exact schema fingerprint. Without this option, the client removes those comments during import. There is no web SQL executor and no production restore command.
- Supports the reviewed `loyalty_latest_claims` view and verifies its table references resolve inside the restored database. Only the current connection's schema qualifier is normalized for comparison. Unknown views, cross-schema references, extra relations and schema-qualified routines are rejected.
- Compares every table's row count and exact value hash, schema/trigger fingerprints, media bytes/metadata and the release hash. It verifies recovered encrypted MFA state, already-consumed recovery state and TOTP replay rejection. It authenticates the matching recovered key and identities before creating a new initialized external policy; repeated recovery into that directory is rejected and hosted readiness must pass.
- Clears restored sessions, challenges and private grants; pending invitations become expired. Durable enrollment and consumed recovery values remain unchanged. Mail/payment/job dispatch stays paused and the source is compared again.
- Writes secret-free verification evidence, with `activationAllowed: false`. CI packages and deploys the same archive that passed, rather than rebuilding it afterward.

The CI job is mandatory for release packaging. A skipped native journey or failed recovery blocks packaging. The required set currently contains fifteen native cases: four repository/guard cases, one accounting case, eight financial transition cases, one billing/accounting workflow and one hosted MFA/operator workflow. Other opt-in native tests are not covered by this claim. Running JavaScript/unit tests alone does not prove native recovery. The rehearsal uses fictional records and does not restore a customer backup.

For local development only, `node --import tsx scripts/verify-staging-native.mjs --local-recovery` performs the same real disposable database/media/key roundtrip with a content inventory of the current source, including dirty and untracked source files. This mode rejects CI and GitHub Actions. Its evidence explicitly records `artifactKind: "source-snapshot"`, `commit: null`, the actual `sourceSha256`, and `linuxRuntimeVerified: false`. It does not verify a Linux application artifact or satisfy the CI release gate. The inventory lists the included source paths; dependency directories, retained local data and private configuration are excluded. No environment override is needed.

## A future real hosting move

Obtain separate review of the source backup, exact archive digest, empty destination, capacity, compatible MariaDB/runtime and dispatch controls. Authenticate/decrypt the archive only into a new private inert directory, inspect it, then perform a separately approved operator native restore. Never execute uploaded SQL through the application or restore over business data. Preserve the matching application-owned key IDs and recover a new initialized external security policy; do not provision an empty policy over existing encrypted records. Verify all current business data, relationships, private file access, mail/payment configuration, MFA and invalidated sessions before approving traffic or dispatch.

`/health` now refuses native deployment acceptance until hosted security initialization/enrollment is ready. First rollout therefore needs a private candidate/setup ceremony before the automated staging switch can accept it; weakening the readiness gate is not a rollout procedure. `/health/live` remains independent.

This procedure and its CI rehearsal are source controls. A successful current CI run and a destination-specific real-data restore remain required evidence before claiming an actual hosting move is ready.
