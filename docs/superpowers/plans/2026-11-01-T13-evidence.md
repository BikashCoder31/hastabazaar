## Reconciliation and implementation

- Read the complete approved retail/category/variant specification, including independent current/candidate 3/100 limits, optional incomplete intake, explicit stock allocation and fresh review/reconfirmation on reintroduction. Existing checkout reserves `products.inventory_quantity` through a trigger; existing cancellation/return/parcel code restores that parent counter. These consumers require T20/T23/T24 integration. No free-text size/colour field was expanded into invented offers.
- Added public-only bounded offer drafts, normalized duplicate checks, exact one-value-per-axis validation and integer-paisa parsing. Three types and 100 included rows pass; paused, zero-stock and browse-only rows still count. 101 included rows and invalid money remain saved private drafts without truncation. Excluded historical rows do not consume the limit. Private costs/profit targets are unsupported in these records.
- Added immutable offer versions/physical identities, one current and candidate head, recorded review/publication decisions, owner and current independent reviewer checks, and both review/publication permissions. Content publication never copies draft stock. A changed physical selection requires a new stable identity; label corrections remain reviewed content. Candidate integration must preserve that distinction in T17/T18.
- Added separately confirmed available/reserved stock, pause state, immutable events and original offer reservations. Explicit quantity confirmation changes only unreserved units. Same-product/same-physical-family transfers check exact base-unit/pack conversion, both current revisions and source availability. Initial confirmation and stock moves are distinct actions; no autosave or publication creates an allocation.
- Retirement retains stock and reservations, marks the old offer for fresh confirmation and leaves all history intact. Reintroduction requires a newly reviewed candidate and explicit current stock confirmation. Release and consumption settle the original reservation once; no refund path automatically restocks it. Actual inspected-return restocking and seller/customer/system orchestration remain T23/T24.
- Explicit legacy mapping requires a reviewed physical-unit/pack/family declaration. It moves the available parent pool once and separately captures existing reserved units and exact old item price/SKU/name. Old unknown selections and physical units remain unknown. The original product/URL/order values are not relabelled. Mapping is never invoked by migration, startup or draft save. A mapped product's old inventory counter is protected from subsequent writes, so incomplete old consumers fail rather than becoming a second pool.
- Added `prepareOfferReservation` for the actual order/payment batch, immutable `OrderOfferSnapshot`, invoice/receipt/return type hooks and native `order_items.offer_reservation_id` binding. The database verifies original customer, product, quantity, price and platform SKU, freezes the same snapshot and rejects reservation reuse. Platform offer SKUs are generated server-side and retained separately from the optional seller stock code. New checkout must use this prepared transaction contract in T20.
- Added additive source migration `0088_product_sellable_offers.sql`, typed tables and source-only MariaDB counterpart/generator wiring. No canonical migration or backfill was applied. Source MariaDB includes binary immutable-text comparisons, exact JSON SKU extraction and guarded legacy decrement; native engine validation remains unavailable.
- Added controlled `VariantEditor`: actual rows, counts, discoverable optional fields, retained incomplete input, separate confirmed/reserved display, explicit confirmation/transfer preview callbacks, and help/photo callbacks. It is a section for the single T17 editor, not a separately launched product flow. The actual workspace must include retained allocations and guide new identities when physical meaning changes; no confirmation/help callback alone claims an operation completed.
