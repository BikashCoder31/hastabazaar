## Additional read-only transport evidence

The schema/runtime agent inspected the actual transport without running it. `OrderMailService.send` returns `Promise<void>`. SMTP in `lib/runtime/node-bindings.ts` observes final DATA250 but discards that evidence; errors carry no typed phase, accepted identity or retry-after. Local capture returns no capture receipt. Both order and business queue catches include transport plus later database writes, so provider acceptance followed by a database failure currently becomes eligible retry. Expired claims likewise cannot distinguish an unstarted attempt from possible handoff. The scheduled runner omits `deliveryTransport`, preventing truthful recovery-contact proof.

The delivery owner should add a backwards-compatible optional delivery context (stable delivery/attempt IDs and Message-ID) and typed provider-accepted/captured results, plus sanitized not-accepted/uncertain failures with phase/category. Legacy void completion must not invent provider evidence. Explicit final DATA rejection is known not accepted; body submission or acknowledgement loss is uncertain; DATA250 remains accepted even if QUIT or database completion fails. Persist handoff-started state before submission, separate transport from database completion, retain result for persistence recovery, and never blindly resend an expired possibly accepted attempt. Message-ID supports correlation, not provider deduplication guarantees. This is implementation preparation only; no SMTP call, setup change or queue processing occurred.
