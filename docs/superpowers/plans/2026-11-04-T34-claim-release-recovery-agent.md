## Findings and correction

Both mounted components wrote complete private draft and pending JSON to sessionStorage. The initial browser RED reproduced the note/reference values in persisted storage for both components (`claim-release-browser-red.tap`, exit 1, 0/3 including parent). The initial native RED was 0/2: historical claim GET returned 400, and an old displayed-actor POST returned 200 and created a claim despite the mismatched actor intent (`claim-release-native-red.tap`).

Claim/release drafts, exact JSON retry bytes and optional file/FormData bytes now remain in their mounted actor/source RAM. Only a versioned actor/source/action/nonce reference is persisted. Legacy values are sanitized without adopting private content; defensible actorless nonces remain unclaimed until an own native receipt proves them. An explicitly different actor or unreadable reference stays blocked and unconfirmed. Unknown optional evidence does not block the required amount-and-date claim. If an opaque reference cannot be saved, the mutation is not sent; its same RAM attempt remains available.

The new GET reader uses immutable command receipt keys and exact actor/action/source/request fields. Claim results also require the original claim event/revision, and completed uploads require their original own file record. Release proof uses its original committed command receipt, not current readiness or a current released flag. Missing actor provenance is unconfirmed; nothing is backfilled. Reads recheck current access and never expire an order, provision an identity, create a file, complete a partial upload, release fulfillment or alter balances. The dedicated release route retains the native `order.manage` boundary and invokes the unchanged release operation. Existing Finance POST compatibility remains.

Customer claim/upload mutations reject a changed displayed actor before reading private bodies. Denial status is processed before JSON parsing, so an HTML 401/403 curtains private details. Retired source callbacks remain inactive. A fresh authorized outcome GET can reopen the same account view while retaining an unconfirmed operation; this does not turn absence into success or permit a replacement request.

A native first-attempt validation/atomic rollback can return a reference-bound `notApplied` attestation. It allows correction only if no earlier result was unknown. Later 400/409, a missing/404 receipt, malformed replies and lost responses retain the original attempt. Reload has no private body to replay and uses GET only. A recorded native result clears the pointer; a bare success status is insufficient.

Additional REDs caught and corrected an implementation timestamp using retry time instead of original receipt time (`claim-release-native-expanded-red.tap`), a post-commit reader 409 incorrectly being marked not applied (`claim-release-postcommit-red.tap`), and an invalid optional file's definite pre-write refusal not allowing correction (`claim-release-upload-refusal-red.tap`). A real native committed claim is asserted in the post-commit test. The handler now distinguishes returned native success from failures before that point; post-commit proof failure never attests absence.

The expanded mounted run was 9/12, exit 1 (`claim-release-mounted-expanded.tap`): native-backed claim/release and prior lifecycle tests passed, but two reauthentication cases retained the denial curtain after a fresh authorized null outcome. After correcting that, a focused run exposed a claim pointer being mistaken for an upload pointer during legacy fallback (`claim-release-upload-scope-red.tap`, 4/6). Upload fallback now reads an actual legacy upload entry only. Both defects and their original assertions remain in final tests.
