## Source and behavior

Read the complete approved bank/identity/payout specification and later single-Super-Admin finance amendment. Reused the checkpoint's registration, payout, receipt, staff authority, public eligibility, notification and review-task infrastructure.

- Source-only `drizzle/0083_protected_change_holds.sql` contains identity/bank revision guards; exact protected cases/permissions; independent new-order/payout holds; immutable private events, identity facts and beneficiary versions; immutable old packet snapshots; explicit retirement/replacement links. All 41 statement chunks load on native ephemeral D1. MariaDB parity is in `deployment/babal/mariadb-protected-change-holds.sql` and the main schema generator. The generated recovery-reset file is only a source artifact and was never executed.
- `protected-change-policy.ts` and `protected-change-requests.ts` distinguish bank-only, unusable-bank/route-dependent, material/unclassified identity and explicitly reviewed same-facts evidence. Current owner, eligible nonconflicted Super Admin, exact versions, actual required proof validity and consumed-once scope are enforced. Missing company proof cannot use one valid identity file to release the case's holds. Bank proof refresh never gets the identity-only exception.
- `protected-identity-change.ts` stores proposed facts/evidence separately, consumes the exact permission, verifies the same legal person/entity, updates current intake answers and document pointers together, and retains immutable old facts and original agreement acceptance actor/time/version/language/form/snapshot. Verification itself releases no holds. Unregistered business changes and ownership transfers cannot be smuggled through this correction path.
- `bank-details.ts` keeps the reviewed account effective until a scoped replacement is actually verified. Full private comparison requires current owner/Super Admin authority and records sensitive access. Normal responses use safe metadata. Ownership evidence, legal ownership basis, reference and explicit hold disposition are mandatory. Existing participation defaults follow the newly reviewed beneficiary; old payment destinations do not change. Linked T07 bank proofs use the bank-case permission/review path; the generic file grant is rejected with a specific route explanation.
- `protected-change-disposition.ts` preserves holds on withdrawal/rejection. Explicit current-evidence dispositions release only the requested resolved scopes. Material identity can revalidate an existing beneficiary without rewriting its history. New-order restoration independently checks current terms, governance, program and product readiness at commit. A concurrent product becoming draft rolls back restoration; releasing new orders leaves the payout hold intact.
- `protected-payout-disposition.ts` requires proof that an invalidated unsent packet never initiated a transfer before retiring it and releasing reservations once. Fresh preparation links to the old packet, including legacy managed settlement-entry links. Ordinary registered rejection/managed cancellation cannot bypass this protected review. Processing/failed/uncertain reservations remain protected; registered truthful outcome recording for an already-processing transfer remains possible. Fixed supplier packets receive the same invalidation/authority guards. Personal beneficiary conflicts are denied; one eligible Super Admin may otherwise prepare, approve and record the authorized outcome.
- Owner and Super Admin exact-case pages expose current/proposed facts, private evidence, first-triage target, immutable history, holds, permission, verification and separate readiness/packet actions. Withdrawal and retained decisions have exact retries. The bank browser form locks the retained uncertain payload; a changed source clears attestations while retaining notes. Timeout/rate-limit retries preserve the original request. API bodies are bounded; malformed JSON and excess size are classified as 400/413.
- Shared notification adapters link document and protected cases rather than creating competing notices. Actual API tests assert one current owner notice after repeated decisions. Review-task projections keep withdrawn/rejected/verified cases actionable while independent holds remain, retain the original deadline, and expose recorded triage instead of pretending the first-triage clock restarted.
