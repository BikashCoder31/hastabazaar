## Reproduced boundary

`getAuthenticatedUser()` previously called `getHostedIdentity()` in a mode that could bind a null `users.auth_subject`, update `users.updated_at`, and renew nonstaff `user_sessions.last_seen_at` even with `activity:false`. A navigation header could additionally renew a privileged session and encrypted MFA proof. Existing-only customer/staff resolvers and displayed-actor rejection happened after those writes. Tests replacing `@/app/auth` did not exercise this behavior.

The initial real-hosted regression produced **1 pass / 11 fail** (`hosted-readonly-red.tap`). Failures included actual null-subject linkage, session activity changes, stale identity acceptance during reads and MFA-proof renewal. The ordinary no-option authentication case passed. After the shared correction it passed **12/12**. Additional existing seller/notification callers then produced **14 pass / 7 fail**, including parent subtests (`hosted-readonly-callers-red.tap`); those failures preceded their caller changes.

## Final behavior and policy boundary

`getAuthenticatedUser({readOnly:true})` forwards an explicit mode to the real hosted provider. It refuses an unbound subject, disables both session and encrypted proof activity updates, and rereads the existing session after assurance checks to reject changed session/account/subject/status/privileged-role facts. No account repair, backfill, invitation acceptance or customer-role creation is authorized by this mode. It retains existing assurance verification; an expired or corrupt signed proof fails closed.

Existing customer API resolution uses this mode. Staff API resolution uses it for both identity checks whenever its existing-only/reject-only options are present. The existing staff intent helper API remains unchanged. Claim/release's direct provider-subject recheck, seller fulfillment's existing-seller helper, seller-center API, seller-terms API, notification-recipient API, and seller notification GET use it. Staff notification GET now uses the existing-only staff intent helper, preventing invitation acceptance on that read. Protected-change original readers inherit the same staff helper; its owner confirmed no independent provider calls.

**Security denial auditing is deliberately retained.** R014 requires a minimal `staff.authorization.denied` record for an identified active staff actor missing a capability. That audit is distinct from forbidden identity/session/business changes and does not grant access. The new test verifies the denial remains denied, exactly that audit is recorded, and identity/role/session/encrypted-security snapshots remain unchanged. A blanket `total_changes()===0` assertion is therefore inappropriate for this denial path. No audit suppression, audit backfill or policy exception was introduced. Unauthenticated and mismatched-intent behavior remains as before, without manufacturing new audit coverage.

Ordinary no-option authentication still links the account proven by its valid hosted session and renews activity. Ordinary customer provisioning, staff invitation acceptance, seller sign-in binding, page authentication, seller-terms viewer/page helpers and unrelated media/form reads are unchanged. The test proves valid ordinary null-subject binding and activity still work. This mode does not replace native business authority guards or route response rechecks and does not promise a transaction-wide snapshot for later business queries.
