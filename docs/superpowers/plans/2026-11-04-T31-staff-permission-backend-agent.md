Existing one-Super-Admin immediate application, legacy pending approve/reject policy, self/target restrictions, profile-version CAS, access-impact journals, native ownership reconciliation, required form answers and published-form policy remain unchanged. ## Wire and native proof

`GET /api/admin/staff-permissions?action=propose|approve|reject&requestId=commandNonce` uses existing-only current eligible Super Admin authentication, exact internal actor intent, original actor/subject and source/physical answer/audit evidence. It never accepts an invitation, applies permissions, reroutes ownership or creates a notification. Current identity/session is confirmed after the private projection; native row images/current source and authority are rechecked.

200 is only `{recorded:true,actorId,action,requestId,sourceId,id,status}`. For proposal, command nonce equals the native request ID and `sourceId` is the target user ID. For approve/reject, command nonce is the **formRequestId**, `sourceId` and `id` are the original proposal ID. A proposal ID is not interchangeable with its later decision nonce. No email, permission array, reason, answers, authenticated subject or current-profile data is returned. Unknown404 and unavailable503 remain `outcome_unconfirmed`, not permission to replace the reference or reapply work.

POST preserves proposal201 and decision200 and adds the same recorded primitive metadata plus `phase:'recorded'`. Before invoking the native mutation, definite input rejection is `phase:'rejected_before_write'`; after invocation it conservatively remains `phase:'outcome_unconfirmed'`, including a409 after lost commit acknowledgment. A later4xx cannot discard an earlier unknown attempt. Root's UI retains exact RAM payload/opaque actor+action+source+nonce references and treats GET as history confirmation, not proof that the original grant is still the currently effective profile.

New native audit metadata binds the original normalized input digest, actual trusted authSubject, action, source, command nonce and original form/answer digest. The exact subject is guarded in the same native batch. Exact replay checks original stored request/answer/proof and current original actor; it does not compare to or reapply the current mutable profile. The actual profile can lawfully change later while the original outcome remains recoverable.

Legacy original request/form/audit facts remain readable with `originalIdentityProof:'legacy_unclassified'`. No original authSubject is backfilled. Existing exact legacy replay is preserved as historical readback of the original retained request fields/physical answer/actor, never a new application; changed inputs are rejected and current effective permissions do not become original evidence. Missing or incoherent original receipt/audit/source stays unconfirmed. No migration or old receipt rewrite was added.

## Reproduced first-profile personal-notice defect

The old notification assertion first exposed the retired `business.permissions.changed` family; current approved T30 access notices use one `business.team.governance` event family for the exact subject and current eligible Super Admins. Reaching that current assertion exposed a genuine runtime gap: a target with no explicit profile was captured as profileNULL, then the same native permission batch inserted its initial profile before executing the notification. The factory's old NOT EXISTS profile snapshot rejected the minimal subject notice.

Canonical `effectivePermissions` includes customer/self permissions even for explicit Admin[]; `account.self.manage` is intrinsic to current staff. The factory now uses one `profileSensitive` predicate for **both** SQL and binding construction. Only this intrinsic self permission skips the profile snapshot; recipient identity, actual current staff role/status, source marker/event, target scope and dedup remain. All non-self permission/profile fences remain unchanged. No new notice family, permission, recipient broadcast or historical replay was introduced.

Two real REDs retain first explicit scoped/empty profile failures (2 messages rather than the required4 for subject+SA). Current tests additionally revoke an unrelated captured SA before the actual batch, verify that recipient is excluded while the current subject/actor receive one copy per channel, prove exact event replay creates no duplicates, and prove the subject's later staff-role loss makes its notice no longer current.

The initial partial fix removed an SQL placeholder but retained its existing-profile bind, causing three meaningful regression failures; `staff-personal-notice-regression.tap` preserves47/50 and the cause. The final shared predicate synchronizes both, with current positive existing/empty/first profiles passing. No failed result is relabeled.

Four outer awaits of genuinely synchronous descriptor builders were removed with Root approval after checking their actual definitions (Team, incident, financial and programme); dynamic imports and all surrounding native read/commit fences remain. Audit assertions retain every original field and add command-proof checks. Notification assertions now verify the actual source event, exact target+eligible SAs/channels, no old parallel family and original creation clock.
