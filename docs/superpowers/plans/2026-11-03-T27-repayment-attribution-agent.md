# T27 repayment attribution implementation evidence — 3 November 2026

Scope: source-only case attribution for identified third-party actual credits, separately approved cash allocation, and original-payer handling of unused excess. This is one T27 slice; it does not complete T27 or downstream workstreams.

The factual receipt payer stays unchanged. One eligible Super Admin records immutable case-specific evidence, reason, public explanation, exact source revisions and a bounded amount. Approval creates neither an allocation nor a native money entry. Unknown payer money remains an owned Finance exception. Explicitly attributed receipts cannot be reused for another case, carrier allocation, payout-return allocation or order/COD allocation. Existing explicitly approved splitting of an original same-owner receipt remains governed by the actual receipt cap.

Attribution and subsequent cash guards count completed-reversal-adjusted actual allocations, remaining actual credit and the current approved case cap, including retained restorations. Current case/source blockers, pending bank reversal, stale receipt/control revisions, changed ownership, revoked authority and personal payer interests prevent approval. Immutable history and the factual payer are retained.

Claim review remains separate from allocation. After case attribution, Finance may match the exact actual gross credit report (including its excess), or a case amount bounded by the attribution and actual credit. This does not settle the debt. Seller projections contain only the reviewed amount, public explanation and time; private payer references, case evidence and reasons stay restricted to Finance.

## Subsequent read-only mixed-receipt reversal audit

A supported integration sequence exposes a completed-disposition gap in source0139. `tests/recovery-mixed-receipt-reversal-acceptance.test.ts` uses inspected fictional memory data to attribute and allocate a credit of original debt plus 1,000 paisa, actually complete the separate 1,000 paisa original-payer return through authenticated/verified destination, fresh verified funding and confirmed outgoing payment, then record a later 5,000 paisa incoming-bank reversal of the recovery portion. The unchanged 0139 path rejects its exact original recovery-allocation disposition at `reconcileRecoveryReceiptReversal` line73 because any retained `manual_receipt_uses` row triggers the blanket `otherUses.length` stop. The return use is correctly retained with state `returned`; no supported transition can erase/release that paid fact. Both opened/reserved and actually completed/returned original-payer return variants are intentionally **RED (0/2)**, `.tmp/t27-repayment-attribution/mixed-receipt-acceptance-red.tap`. No 0139 production/shared file was modified for this audit.

The narrow proposed repair is to recognize proven completed original-payer receipt returns as unaffected retained uses while continuing to block unknown/order/COD/pending/uncertain uses. Prove the exact original payer, receipt, return amount, completed obligation and paid packet at commit; subtract retained return uses from the API unallocated-origin capacity (the storage proof already subtracts manual uses). A reversal explicitly assigned only to an existing recovery allocation can then restore only that still-valid original unpaid portion without changing the completed excess return or inventing debt/loss. Do not just remove the broad guard or classify returned money as unused.

Separately, a customer-refund-return credit which was retained and actually reissued to the customer has no discovered completed disposition for a still later incoming-bank reversal of that credit. The generic bank reversal is retained as an owned Finance exception; there is no existing recovery allocation for 0139 to reverse, and the completed retry has `source_kind=receipt_return`, intentionally excluded from recording another original merchandise-refund reversal. The customer-refund agent independently confirmed no alternate supported completion path. This is a disclosed owned-disposition gap; it does not authorize renewed seller/customer debt, editing paid facts, or marking the exception resolved.

The acceptance file now covers both `reserved` and `returned` uses; both fail at the same blanket 0139 rejection (final audit run 0/2, 7.0 seconds). A completed-only allowance repairs the first demonstrated case but leaves a supported reservation lifecycle dead end: after an incoming reversal, the existing actual-receipt coverage check prevents completing the return, while the return reservation prevents reversal reconciliation. For an explicitly identified recovery-only reversal with adequate exact post-disposition coverage, the original-payer return reservation should be retained untouched, including any existing processing/uncertain outgoing outcome. Recognizing it as an unaffected valid use must not infer that a transfer completed, release a reservation, classify paid/reserved money as unused, or authorize another transfer. Root review is required to settle the smallest proof boundary; no shared production source changed during this audit.
