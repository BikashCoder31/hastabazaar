# Staff invitation backend and actor boundary

This is the bounded backend half of Root's A07 follow-up. The canonical Team policy keeps a pending invitation separate from effective authority and email delivery separate from acceptance. Existing published invitation/permission contracts remain in force: these forms are outside the exact57 native-default transition. No fallback publication, permission grant, acceptance rule, or business approval policy was added.

## Current contract

- `requireStaffApi(permission, {intendedActorId})` rejects a different or missing existing staff identity before invitation acceptance, bootstrap, or invitation-expiry writes. It compares internal actor ID and the authenticated subject exactly, confirms the session again, and proves the current database subject/role before returning. An explicitly supplied empty options object means existing-only. Calling without options preserves normal mailbox-proven invitation acceptance.
- `requireStaffIntentApi(request, permission[, expectedActorId])` applies the header before provisioning and checks the returned actor again. It uses the existing staff alias so bounded auth fixtures remain compatible. Team GET/POST, invitation POST/DELETE, and permission POST use this helper; no other Team/permission logic changed. `requireExistingStaffIntentApi` makes the new outcome GET read-only even when the header is absent.
- POST returns201 for creation or200 for an exact recorded retry, with `recorded`, `requestId`, trusted internal `actorId`, original invitation ID/expiry, and current status. An exact retry never sends mail. New creation audit metadata binds the original normalized command digest and authenticated subject; mutable invitation grants cannot redefine the original input.
- GET `?requestId=...` requires current eligible Super Admin authority and the original actor/source/physical receipt. It returns only `{recorded:true,requestId,id,expiresAt,status}`; no email, permissions, form answers, subject, or token. Missing proof is404 `outcome_unconfirmed`, unavailable proof is503. It never resends mail. Current actor/subject/role/source facts are rechecked after asynchronous projection.
- Legacy audit records without the new command proof retain factual creation readback, explicitly adding `replayable:false` and `originalInputProof:'legacy_unclassified'`. Original permissions/authenticated subject are not fabricated from current grants. Both original and changed-input POST replay remain rejected; old audit/history rows are unchanged.
- POST failures are `phase:'rejected_before_write'` only before invoking the native creation command; after invocation they conservatively remain `phase:'outcome_unconfirmed'`. Recorded responses use `phase:'recorded'`. A readback failure after a genuine commit is not mislabeled a validation rejection. Client references must remain opaque and must not be replaced automatically.
- The legacy mail helper returns void. POST reports `emailDelivered:false` and whether that helper was invoked, without claiming provider acceptance/capture. Stub invocation counts are not delivery proof.
- DELETE retains the original pending-only lifecycle/409 behavior and audit atomicity, with trusted original authSubject guarded in its actual batch. Acceptance/revocation authority remains native.
