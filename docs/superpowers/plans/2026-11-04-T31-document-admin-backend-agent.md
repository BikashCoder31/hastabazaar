## Original evidence and wire contract

Both `/api/admin/seller-documents/[id]/review` (and its `verify` alias) and `/api/admin/seller-document-change-requests/[id]` now support existing-only, no-write `GET ?commandId=originalNonce`. Authentication uses the rendered internal actor identity and actual authenticated subject. Native current Super Admin authority, original actor/source/nonce, immutable business audit proof, the unchanged immutable generic command receipt and final current session/source/subject are checked. Readers do not execute prepared guard statements or accept/provision staff. Original history is independent of the current action control or a later lawful permission decision.

Successful POST and GET return the same sanitized primitives: `{ok:true,recorded:true,requestId,actorId,action:'review'|'permission',sourceId,id,decision,historical:true}`. The decision is the original input decision, not an assertion that a previously approved permission is still currently effective. Missing or unproven original history is GET404 `{recorded:false,requestId,action,sourceId,code:'outcome_unconfirmed'}`. A retained string receipt without original authenticated-subject proof remains unconfirmed; GET does not backfill or adopt it. Post-write readback failure is503, not proof that no decision saved. Exact replay never issues another grant, notice or decision.

New staff business audits append their original request ID and private `commandProof` containing the trusted original subject and normalized original command payload. Existing `seller.document.*` audit immutability/retention guards protect this proof. The existing generic `commandReceipt` source, digest payload and string result are unchanged, preserving seller request/correct/replace and direct native callers. Direct historical/domain callers without a trusted subject do not manufacture one. API callers pass the real subject, and its exact ID/subject pair is guarded in the same write batch. A later subject rebound cannot read or adopt the original API outcome.

## Definite rejection versus unknown outcome

Only `DocumentDecisionBeforeWriteError` emits `{phase:'before_write',actorId,action,sourceId,requestId}`: native reason/decision validation, or an actual freshly read missing/stale/status-conflicting source or missing protected-case linkage detected before entering a write batch. The original immutable receipt check precedes source preflight, so an exact recorded replay does not become a new current-source decision. Existing atomic guards still reject authority/source changes after the preflight.

Content-digest conflict, batch/commit error, arbitrary exception, missing legacy proof and readback failure remain `outcome_unconfirmed`. The marker describes **this invocation only**. A later409, even with a correctly matched before-write marker, cannot erase an earlier unknown attempt. The UI must retain that reference and exact original RAM request until original evidence confirms it; Root implements and tests this distinction. Malformed API-envelope/auth failures without a complete trusted reference do not receive invented before-write proof.
