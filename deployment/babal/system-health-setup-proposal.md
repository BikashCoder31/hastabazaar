# System health monitor setup proposal

Status: source and isolated tests only. No scheduler, endpoint, contact, credentials or deployment has been enabled. Use alongside [the email automation proposal](email-automation-setup-proposal.md); keep the existing single sender/evaluator job.

The independent monitor invokes authenticated `POST /api/jobs/system-health` once a minute. The endpoint runs the actual local liveness handler, read-only database/security/form readiness checks, bounded form/file observation evaluation and incident ownership reconciliation. It never seeds, migrates, resets, repairs data or replays business actions. Its response identifies the trusted runtime environment and release. Local handler success is not proof of every public/customer journey or external availability.

Reuse `scripts/email-automation-watchdog.mjs` with a separate mapping containing `healthKind: "system"`, `expectedReleaseId` equal to the released application's `HASTABAZAAR_RELEASE_ID`, and `healthUrl: "https://APPLICATION-HOST.invalid/api/jobs/system-health"`. All independent host/scheduler/contact evidence and transport restrictions in the email proposal apply. Use separate reviewed `statePath` and `lockPath`; never reuse or overwrite the email monitor's retained episode state. Start with `enabled: false`, unreviewed mappings and an unset original `expectedSince`; these deliberately cannot execute.

The system monitor expects exactly `application.availability` and `database.readiness`, each with an explicit incident projection or null. Two distinct failed observations, five minutes of missing expected observations, or an already open persisted incident opens attention. Keep the original failure time. Recovery requires two fresh current-release healthy observations at least one minute apart, and no open incident. A release change clears the recovery observation pair while retaining the original outage episode and clock. Ordinary governed incidents remain open until authorized evidence-based closure; a single returning green response is insufficient.

Provision `SYSTEM_HEALTH_JOB_SECRET` on both the application and independent monitor, and `SYSTEM_HEALTH_CONTACT_SECRET` only on the independent monitor. Credentials belong in reviewed protected environment files, never JSON, URLs, command arguments or logs. On the application, map `HASTABAZAAR_RELEASE_ID` and the original `SYSTEM_HEALTH_EXPECTED_SINCE` in milliseconds. Missing metadata stays Unknown/unavailable; do not label historical observations as belonging to a new release. New release identifiers must identify the reviewed source artifact, including approved uncommitted source if applicable, rather than claiming an old Git commit alone is the new build.

The concrete installation template is commented in [the cron example](email-automation-cron.example). It requires verified Node/flock behavior, the exact host paths, separate process boundaries, bounded execution, actual eligible on-call identities and an independently reachable contact. Review provider acceptance/idempotency/rejection semantics before enabling contact retries. An ambiguous contact handoff remains uncertain; restarting the process must not resend it automatically. No real contact probe is authorized by this local implementation.

Local proof: `tests/email-automation-watchdog.test.ts` exercises fake network and memory state, including the actual system-monitor response contract; `tests/system-health-monitor.test.ts` exercises the actual protected route, read-only failure, retained heartbeat, release isolation and common governed notices using disposable databases. This does not establish the target host or recipients. Later explicit deployment authorization and concrete mapping remain required. The deferred backup program is not enabled by this proposal.
